# ADR 0052：同会话未完成计划原地恢复

- 状态：Accepted
- 日期：2026-08-13
- 继承：ADR 0025、ADR 0045、ADR 0051

## 背景

`dgoal-work-v1` 已在 Pi session 分支中同步持久化 current Goal、唯一 Work List、可选 Plan Contract 与完整 pending proposal。进程退出或宿主中断后，这些事实仍在，但旧行为会让恢复的 proposal 在后续 `agent_end` 自动弹确认，也会让 active Plan 继续 continuation；两者都可能在用户尚未重新建立上下文时执行或重复外部副作用。

仅凭持久态无法可靠区分 crash、正常退出或用户稍后返回，因此不能声称“检测到崩溃”。另建 `.plans/`、Plan 副本、跨 session 索引或可恢复 History 又会违反 ADR 0051 的单一 current Goal / Work List 与 History 只读边界。

## 决策

1. 恢复范围只限同一 Pi session 当前分支最新一条 `dgoal-work-v1`。其中 current Goal 必须完整合法；无效时 fail-closed，不回退复活更旧的 active Plan；无效 pending proposal 不恢复。`fork` 是新 session；运行时追加仅含当前 session ID 的 `dgoal-session-scope-v1` 边界标记，只读取该标记之后的本地 Plan / History，从而忽略宿主复制来的父 session 状态。恢复不搜索其它 session，不导入 Plan，不恢复终态 History。
2. 冷 `session_start` 的 `startup | resume` 原因才触发未完成 Plan 安全恢复：
   - 完整 pending proposal 保持 pending，显示 `/dgoal review`；
   - active Plan Contract 在 status / overlay 前原地追加为 `paused(session_recovery)`；
   - Goal ID、Plan Run ID、Work List、revision、check、evidence 与已完成项保持不变。
3. `reload`、`session_tree`、`session_compact` 只做结构重同步；soft Work List 只恢复结构，不进入 recovery pause。compaction 的既有 active continuation 规则不变。
4. proposal 自动确认需要当前进程内的新鲜启动因果标记。该标记不持久化；恢复 proposal 后的 `agent_end` 不弹窗、不重试。用户必须显式运行 `/dgoal review`。
5. `/dgoal review` 支持确认、反馈、显式拒绝和延后。Esc、空反馈、旧宿主 confirm=false 与 UI throw 都保留 proposal；若现有 Plan 随后只发生暂停/恢复，合法的 upgrade proposal 仍可 review。upgrade proposal 持久化原 Goal/Work List/Contract 基线指纹；新进度、evidence、check 或 Contract 变化会使旧提案失效，不能覆盖当前事实。一次 proposal 同时只允许一个确认 UI；session generation、Goal/Contract/revision、基线指纹与 proposal 不匹配时丢弃迟到选择。
6. `/dgoal resume` 遇到 pending proposal 时先要求 review。恢复 `paused(session_recovery)` 时，首轮 prompt 必须先核对所有 `in_progress` 与工作区/外部副作用；无法确认是否已发生时 blocked 或询问，不得猜测重放。
7. 不新增 Goal 状态或 Plan 副本。`session_recovery` 只是新的 `PauseReason`；`dgoal-session-scope-v1` 是唯一新增的持久边界元数据，只含 session ID，不承载 Goal、Plan 或 History。确认 UI 的新鲜因果与 in-flight 锁只存在内存。
8. proposal 确认、resume 与反馈重提不把 `sendUserMessage()` 当成送达回执。正在运行的 agent 只能排队，必须等 `agent_settled` 后以独立空闲 turn 投递，不走不触发 `before_agent_start` 的 streaming `followUp` 路径。运行时给 extension input 追加严格绑定的一次性 marker：`input` 先复核 session generation、Goal/Contract/revision 与 proposal，新 Plan 的 START 还先落 paused checkpoint；`before_agent_start` 只对最终 prompt 做预检，系统提示仅保留固定 guidance；精确匹配的 user `message_end` 才在宿主已有有效 abort signal 时提交 active，并同时从会话与 provider 输入中清除内部 marker。此后 `context` 才把已提交 Plan 投影到当前请求消息尾部，投影不写入会话历史（缓存兼容调整见 issue #3）。marker 缺失、改写、迟到或状态不匹配都在该可取消边界 fail-closed。
9. 反馈重提在新 proposal 通过语义预审并持久化前始终保留旧 proposal。一次反馈改写 turn 未产生合法新 proposal 时，不得落入底层 Plan execution continuation；结束本次改写并保留 `/dgoal review` 入口。认证、模型、预审或新 turn 启动失败同样不删除旧 proposal。参与恢复、暂停、清除、History、fork scope 与投递状态转换的任一 `appendEntry()` 抛错都按“当前 `SessionManager` 的内存 leaf 可能已先改变”处理：保留安全内存投影并硬锁该 manager，禁止任何后续 dgoal append、mutation 与 continuation；不得从不确定 leaf 追加补偿子节点。extension reload、tree 与 compact 复用同一 manager，不能解除隔离；真正重建 manager 后仅从磁盘最后完整记录恢复。若持久会话 JSONL 末尾不完整或不可读，继续 fail-closed，要求先修复或更换会话文件。
10. 状态、History、前文承接与审核工作区推断必须由宿主提供当前分支 `getBranch()`；能力缺失时返回空状态或当前 cwd，不能降级到代表整棵 session tree 的 `getEntries()`。resync 读取失败或 shutdown 会先使当前投影失效；在下一次成功读取当前分支前，任何命令、工具或持久化入口都 fail-closed。所有跨 `await` 的 UI、语义预审和状态提交都绑定原 session generation 与状态快照，不能写入后来切换的分支。

## 结果

- 用户意外退出或返回旧 session 时可以继续同一计划与进度，不需要重建或把计划写入项目文件。
- 恢复默认 fail-closed：没有自动 prompt、自动弹窗或自动外部写入。
- 用户确认与真正启动之间若被中断，持久态最多停在可人工恢复的 paused checkpoint，不会自动重放。
- 当前 session 分支仍是唯一状态权威；Plan Run History 继续只读、不可 resume。
- 产品文案只能说“发现未完成计划”，不能说“检测到 crash”。

## 未选择

- `.plans/PLAN.md`、全局 Plan 库或跨 session 搜索：形成第二状态所有者并可能恢复错工作区。
- clean-shutdown lease / heartbeat：为区分 crash 增加额外时序状态和误判面，当前收益不足。
- 自动恢复 active 与 continuation：可能重复文件、网络、支付、部署等不可逆副作用。
- 把 History 重新激活：破坏终态与归档语义。
