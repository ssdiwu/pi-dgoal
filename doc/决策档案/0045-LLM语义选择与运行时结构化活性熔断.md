# ADR 0045：LLM 语义选择与运行时结构化活性熔断

> Status：已接受，已实现。

## 背景

pi-dgoal 会在 Plan 保持 active 时自动续跑。早期 `no_progress` 只识别“整轮没有工具调用”：任意工具一旦执行，就会把该轮视为有效推进。真实长会话因此出现持续 `read`、`plan_read`、查询与状态汇报，却没有文件、Plan 或独立审核结果变化；每轮都有 activity，原有熔断永远不会触发。

这不是靠更多关键词就能可靠解决的语义问题。同一条 `bash` 命令可能是关键验证，也可能是重复查询；同一段 assistant 文本可能诚实说明阻塞，也可能只是继续承诺。运行时若解析自然语言、命令字符串、文件扩展名或工具名称来猜“是否真的在工作”，会复制 ADR 0037 已拒绝的语义词表问题，并把自定义工具和未来执行方式锁进不断扩张的规则库。

但把活性完全交给主 LLM 自报也无法形成可靠兜底：模型可能连续判断“继续”，实际却只重复读取、查询或口头汇报，造成无限续跑和 token 消耗。需要把“下一步语义选择”与“外部可观察的活性保护”分层。

## 决策

### 1. LLM 负责继续推进或结构化暂停的语义选择

从活性角度，主 LLM 每轮只有两类合法出口：

1. **继续推进**：直接执行当前合法动作、委派可执行 task、根据结果修复，或把已完成事实写成结构化 Plan 状态与 evidence。正常完成是继续推进后的合法收口，不是第三种停滞解释。
2. **结构化暂停**：只有确实缺少用户才能提供的决策、信息或授权，且当前目标无法自主闭环时，调用 `plan_update(target=goal,status=paused,reason=...)`。纯文字表达“被阻塞”不改变状态。

是否继续、下一步做什么、某次测试或查询对当前目标意味着什么，都由 LLM 结合目标和上下文判断。运行时不替代这项语义判断。

### 2. 运行时只观察结构化活性，不解析语义

运行时不读取 assistant 文本来判断进展，也不解析 `bash` 命令字符串、源码含义或工具参数来猜动作价值。它只消费宿主可观察的结构化事件，并区分：

- **activity（工具活动）**：本轮调用过工具；
- **durable progress（持久进展）**：本轮产生了可跨轮观察的文件、Plan 或独立 check 终态。

当前持久进展基线包括：成功 `edit` / `write`；task/phase/goal status、task evidence、blocked 结构或任务集合变化；独立 check 写出 `approved` / `rejected` 终态。`read`、`plan_read`、`bash`、未知工具、失败写入、无终态 check、仅修改 `objective` / `subject` / `description` 的文本更新与 no-op Plan 更新只算 activity。

这份基线是结构化事件契约，不是动作语义词表。未来工具若要声明持久进展，应提供明确、可测试的结构化结果，而不是让运行时解析自由文本或命令内容。

### 3. 使用双层活性熔断兜底

运行时保留两条互补计数：

- 连续正常结束但完全没有工具 activity，触发硬熔断；
- 即使持续有 activity，连续多轮没有 durable progress，触发软熔断。

当前实现阈值分别为 3 轮与 8 轮。数值是可由回归证据调整的实现参数；不可退让的决策是“双层观测 + 结构化信号 + 最终强制暂停”。两条路径继续使用现有 `paused(no_progress)`，通知可区分 `no_tool` 与 `activity_only`，不新增 Goal 状态、持久化枚举或调度器。

阈值前，continuation 逐级提醒 LLM：继续就直接执行或委派；真实用户决策死锁则结构化暂停。若 LLM 仍连续选择“继续”却没有产生持久进展，达到阈值后运行时强制暂停，避免把是否停止再次交给已经空转的同一判断循环。

### 4. 结构化结果是 LLM 语义判断与运行时活性观测的接口

运行时不需要理解 `npm test` 是否重要。LLM 读取测试结果后自行决定：继续修复、继续验证、结构化暂停，或以 `plan_update(..., evidence=...)` 记录已经成立的完成事实。只有最后一步形成 Plan 状态或 evidence，运行时才把该语义判断观察为持久进展。

因此，“不解析语义”不等于忽略 LLM 判断，而是要求 LLM 把关键判断落实为可观察、可测试的结构化结果；自由文本本身不成为活性事实。

## 与既有决策的关系

- 延续 ADR 0031 的主动暂停语义；工具入口按 ADR 0038 统一为 `plan_update(target=goal,status=paused,reason=...)`。
- 扩展 ADR 0037 的职责分层：0037 处理 proposal 语义与执行护栏，本 ADR 处理自动续跑期间的语义选择与活性兜底。
- 扩展 ADR 0038 的固定技术熔断：三档 Plan 共用本 ADR 的双层活性判断，不增加新的 Plan 类型或状态。
- 不改变 ADR 0044 的审核检查点持久化边界；独立 check 只有稳定终态才构成持久进展。

## 权衡与后果

- 运行时不会因为 assistant 声称“正在推进”或重复调用只读工具而无限续跑。
- LLM 保留业务语义所有权，不需要为 `bash`、自定义工具或源码建立脆弱的语义解析器。
- 纯 `bash` 验证即使有业务价值也只算 activity；LLM 需要继续执行，或把成立的结果写入 Plan evidence/status。代价是少数长验证流程可能先触发提醒，但不会被错误宣布完成。
- 未声明结构化副作用的新工具默认只算 activity。这是保守选择：可能提前暂停，也不允许未知工具无限重置熔断。
- 回归测试必须同时覆盖：无工具硬熔断、只有 activity 的软熔断、真实持久进展清零、仅文本/no-op 更新不清零、失败或无终态 check 不清零，以及 start/resume/resync/clear/finalize 的计数隔离。

## 放弃的方案

1. **解析 assistant 文本判断是否在工作或阻塞**：自然语言不稳定，声明不可复验，也会鼓励用文字绕过熔断。
2. **解析 `bash` 命令或工具参数判断动作价值**：同一命令的价值依赖目标上下文，词表会不断扩张并误伤自定义工具。
3. **只降低无工具阈值**：无法处理持续 `read` / `plan_read` 的 activity-only 空转，还会误杀正常的一轮解释或总结。
4. **完全相信 LLM 自报“继续”或“有进展”**：缺少外部停止条件，无法阻断导致本决策的无限续跑故障。
5. **新增调度器、预算状态或新的 pauseReason**：扩大状态机但不提升语义可靠性；现有 `no_progress` 已足以表达技术性活性暂停。
