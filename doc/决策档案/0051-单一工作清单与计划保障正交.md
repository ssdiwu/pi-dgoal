# ADR 0051：单一工作清单与计划保障正交

> Status：已接受，v0.8.1 实施中。本决策取代 ADR 0038 中“所有 Plan 共享 phase → task 树、Task Plan 使用隐藏 phase、Plan 类型冻结结构与固定八工具”的核心建模；v0.8.0 现行代码在迁移完成前仍以 ADR 0038 为实现事实。

## 背景

ADR 0038 用同一份 goal / phase / task 数据结构承载三档 Plan，换取了统一 reducer、持久化与 TUI。但统一发生在错误层级：`TaskPlan` 只有 `phases`，所有 task 必须先属于 phase。Task Plan 因而制造一个对工具与用户隐藏的 phase；只做 goal 终审的 Phase Plan 也必须创建至少一个 phase，哪怕真实工作没有阶段边界。

这形成了四个问题：

1. 普通多步工作只能直接升级成 Until Done Plan，缺少可先建立、跨 turn 保留但不自动续跑的软性工作清单。
2. Phase 同时承担真实阶段、通用任务容器和审核 scope，结构与保障强度耦合；隐藏 phase 需要在工具、持久化、prompt、TUI 和测试中持续打补丁。
3. `Task / Phase / Goal Plan` 的名称同时暗示内容层级和审核密度，实际却是 Phase Plan 只做 goal check、Goal Plan 同时做 phase/goal check，字面无法说明保障责任。
4. goal 完成后当前状态被清空，`/dgoal s` 只能看到活动 Plan；已有 `finalAuditHistory` 只是单次终审修复输入，不是可回看的 Plan Run History。

外部 Todo / checklist 机制与 dgoal 的 Until Done / 独立建检解决不同问题。前者应成为软性工作底座，后者应作为可选完成合同附着其上，而不是继续让轻量工作借用审核计划的数据形状。

## 决策

### 1. Goal 只拥有一张 Work List

同一 Pi session 同时最多有一个当前 Goal；该 Goal 只拥有一张逻辑 Work List。Work List 是唯一的条目、依赖、状态、持久化和 TUI 状态所有者，不拆成“计划内 / 计划外”两张清单，也不维护逐条 Plan 绑定或豁免标记。

Work List 在没有 Plan Contract 时先作为软性工作集存在：

- agent 可为普通多步工作主动建立；
- 未完成内容跨 turn 保留，但不会触发 synthetic continuation；
- agent 可按新证据拆分、合并、删除、重写或重排 Work Item；Work Item 此时可以模糊或复合，不要求每项已经是独立可执行 task；
- Goal 与 Work List 被清除或替换前保持当前会话唯一，不形成多目标池。

### 2. Phase 是同一 Work List 内的可选组合节点

Phase 不再是所有 Work Item 的必经父节点。Work List 可保持完全平铺；只有真实工作存在阶段边界时才建立 Phase。

Phase 的固定语义是：

- 它是同一 Work List 内的特殊组合节点，不是第二张可独立管理的 Work List；
- 它自身不承担直接工作，实际工作由其成员 Work Item 完成；
- Phase 不允许嵌套，多个 Phase 按确认顺序严格串行；
- 所有真实 Phase 都必须由主 agent 显式收口。成员 Work Item 耗尽只形成语义决策边界，不自动写 Phase done；
- 分阶段建检计划还要求当前 revision 的 `phase_check` approved，随后仍由显式 update 写 Phase done。

执行计划与目标建检计划可以按真实结构使用 Phase，但不得为了复用 reducer、持久化或 UI 而制造 Phase。分阶段建检计划因其保障责任必须至少有一个真实 Phase。

### 3. Work List 优先，Plan Contract 按需升级

普通工作先建立 Work List。后续发现需要持续完成、目标终审或逐阶段建检时，agent 在同一个 Goal 和同一张 Work List 上重组当前工作，并建立或升级 Plan Contract。

升级不是字段复制或状态翻转：agent 可根据当前证据对 Work Item 做一对多、多对一或多对多重组，并按真实边界建立 Phase。升级后的 Work List 整体服从当前保障预设，不并存条目级计划豁免；升级前已完成的前置工作仍可留在同一清单中，升级时必须被归一为新合同可接受的结构化事实。

同一次 Plan Run 的保障等级只允许单向提高，沿用 Goal、Work List、开始时间和运行身份，并记录 profile transition 与 revision：

```text
执行计划 → 目标建检计划 → 分阶段建检计划
```

不得在同一次运行内降低保障。需要降级时，用户必须显式结束或清理当前 Plan，再建立新的 Plan Run。

### 4. 三档名称只表达保障责任

Work List 本身不是 Plan。Plan Contract 只使用三个固定保障预设，不开放可任意组合的策略开关：

| 保障预设 | 自动续跑 | goal_check | phase_check | Phase 要求 | 激活边界 |
|---|---:|---:|---:|---|---|
| **Execution Plan（执行计划）** | 是 | 否 | 否 | 可选 | agent 可主动建立或升级 |
| **Goal Check Plan（目标建检计划）** | 是 | 是 | 否 | 可选 | 用户显式启动并确认 |
| **Staged Check Plan（分阶段建检计划）** | 是 | 是 | 是 | 至少一个真实 Phase | 用户显式启动并确认 |

AI 负责判断是否建立 Work List、是否升级执行计划以及如何组织工作；用户负责选择是否引入 goal 或 phase + goal 的独立保障。Goal Check / Staged Check 的 acceptance contract 继续受启动闸门、语义预审和用户确认保护。

### 5. 任务耗尽、check 与显式完成继续分离

Work Item 耗尽只说明当前候选工作已用尽。主 agent 必须对照当前 Goal / Phase Description、显式交付物、适用的冻结验收契约与最新 rejected feedback，决定新增或重组 Work Item，还是进入完成链。

- Execution Plan：Work List 耗尽后新增/重组工作，或回读结构化工作与交付物后显式关闭 Goal；无独立审核。
- Goal Check Plan：真实 Phase（如有）逐个显式收口；所有工作充分后运行 `goal_check`，approved 后再显式关闭 Goal。
- Staged Check Plan：当前 Phase 工作耗尽后先决定是否补充工作；充分时运行 `phase_check`，approved 后显式关闭 Phase；全部 Phase done 后运行 `goal_check`，approved 后显式关闭 Goal。

`check` 只记录审核事实，显式 update 才改变 Phase / Goal 完成状态。Description 继续指导执行而不成为平行 acceptance contract；交付物逐项证据、revision 失效、独立验收与用户复核分离继续保留。

### 6. 公共工具改为 Work List + Plan Contract 职责面

v0.8.1 使用九个两词公共工具，不保留 `dgoal_` 前缀：

| 职责 | 工具 |
|---|---|
| 建立软性 Work List | `work_list` |
| 建立或升级三档 Plan Contract | `execution_plan`、`goal_plan`、`staged_plan` |
| 管理唯一 Work List | `work_create`、`work_read`、`work_update` |
| 独立审核 | `phase_check`、`goal_check` |

`work_list` 在软性状态下建立或整份重写当前 Goal / Work List；`execution_plan` 可由 agent 主动建立或升级；`goal_plan` / `staged_plan` 复用显式启动闸门。`work_update` 是 Work Item、Phase、Goal 状态与显式完成的唯一 agent 写入口；check 继续不得代写 done。

旧 `task_plan`、`phase_plan`、`plan_create`、`plan_read`、`plan_update` 删除，不保留永久双轨。旧 `goal_plan` 名称在新版本中改为 Goal Check Plan 语义；原“phase + goal 双审”入口由 `staged_plan` 承接。这是明确的破坏性公共工具变更。

### 7. Plan Run History 只归档终态计划

`/dgoal s` 增加 `Current（当前）` / `History（历史）` 顶层视图。History 只保存进入过 Plan Contract 的终态 Plan Run，不记录纯软性 Work List，也不记录每次 Work Item 拆分、合并或状态修改。

- `done`、`cleared`、`superseded` 等全部真实终态都归档；
- 历史随当前 Pi session 持久化，跨 turn、session compact 与同一 session 恢复可见，不跨独立 session 聚合；
- 每条记录保存 Goal、最终 Work List / Phase / Work Item 结构、保障等级变化、时间、完成声明、交付物证据和 check 元数据；不保存原始 auditor report、thinking 或完整 transcript；
- 历史只读，不可恢复为 active Goal，不构成多目标池或 scheduler；
- `/dgoal clear` 结束当前状态但不等于删除历史，历史删除使用独立且需确认的动作。

### 8. 使用新的持久化世代，不兼容旧活动状态

v0.8.1 使用新的 Work List 持久化键；`dgoal-plan-v2` 及更早活动状态不迁移、不恢复，也不建立运行时兼容分支。新持久态同时承载当前 Goal / Work List / Plan Contract 与当前 session 的 Plan Run History；恢复仍采用 branch 内结构化事实而非 transcript 推断。

具体键名、严格 schema、ID 分配和 last-write / append 边界由版本实施方案确定，但必须保持 Goal Runtime 单一写入所有权、UI fail-soft、旧分支迟到审核不得写回新状态等现有安全边界。

## 保留的既有决策

本决策改变结构与产品档位，不降低以下已实现边界：

- ADR 0016：独立验收条件与用户复核分离，审核器不得扩张冻结完成门；
- ADR 0019 / 0036 / 0037：高保障计划必须由真实用户显式激活；代码管授权与结构，LLM 管语义，执行工具管真实动作；
- ADR 0025：Goal Runtime 独占可变 session 状态；
- ADR 0039：Phase / Work Item 继续使用类型化引用与各自编号，禁止无类型数字引用；隐藏 Phase 相关结论失效；
- ADR 0042：Goal / 可见 Phase 的 Description、计划态 Work Item 的执行说明、删除 `contextSummary`、两层详情浏览与 Description 非审核门继续保留；软性 Work Item 在升级前不被强制加重；
- ADR 0045：LLM 负责语义选择，运行时只观察结构化 activity / durable progress 并用双层熔断兜底；软性 Work List 不启动 continuation；
- ADR 0046–0048：显式交付物逐项留证、压缩后结构化状态优先、工作耗尽先形成主 agent 决策边界；
- ADR 0049 / 0050：AI 主导的轻量执行计划在 `no_progress` / `model_error` 下保留受限恢复能力；用户确认的高保障计划继续显式恢复；
- ADR 0014 / 0015 / 0028 / 0030 / 0043 / 0044：审核候选链、局部 revision、检查点和迟到结果隔离；
- ADR 0008 / 0009 / 0010 / 0040 与 TUI 容错文档：层级/状态视觉编码、软遗忘、人类可读投影和 UI 不拥有状态事实。

## 取代关系

- **取代 ADR 0038 的结构与类型核心**：不再共享强制 phase → task 树，不再使用隐藏 Phase，不再冻结 `Task / Phase / Goal` 结构类型，也不再固定原八工具；保留 check / update 分离、显式高保障授权和固定技术熔断。
- **部分取代 ADR 0039**：保留类型化 ID 与独立编号；删除隐藏 Phase 及其编号后果。
- **部分取代 ADR 0042**：软性 Work Item 不要求预先具备计划态 Description；Goal、真实 Phase、升级后的计划态 Work Item、`contextSummary` 删除和 TUI 浏览边界保留。
- **扩展 ADR 0045–0050**：把其中 Task Plan 专属语义迁移到 Execution Plan，并在前面增加不自动续跑的软性 Work List。
- **取代路线图“不新增历史”的边界**：新增只读 Plan Run History；仍不新增 mutation log、跨 session 账本或恢复池。

## 后果

- 普通多步工作先得到轻量、可跨 turn 的结构化清单；只有真实需要时才承担 Until Done 或独立建检成本。
- Goal、Work List、Phase 与保障等级各自只承担一种职责；隐藏 Phase 及其跨工具、状态、持久化和 TUI 特判可以整条删除。
- 一次工作可在同一 Plan Run 内逐步提高保障，历史不会因升级被切碎，也不会允许 agent 静默撤销用户确认的保障。
- 公共工具、数据模型、持久化键、prompt、TUI 和主要测试夹具都会发生破坏性变化；必须以单路径切换删除旧实现，不保留双轨适配层。
- Plan Run History 增加 session 持久化体积；通过只记录终态结构、裁掉 auditor report / transcript、禁止 Work Item mutation log 控制增长。
- Work List、Plan Contract 与 Phase 的正交关系会增加一次明确的升级归一动作，但避免长期维护隐藏容器、结构类型切换和条目级计划豁免。

## 未选择方案

- **继续保留隐藏 Phase**：实现改动最小，但根因和所有特判继续存在。
- **Goal 下维护计划内 / 计划外多张 Work List**：会引入绑定、完成排除、双层浮层和多状态所有者。
- **单 Work List 内按 Work Item 标记计划豁免**：只是把计划内外拆分下沉到条目级，仍需长期维护双语义。
- **自由组合 goal / phase check 开关**：表达力更高，但增加非法组合和用户配置成本；固定三档足够表达已确认保障等级。
- **Phase 任意嵌套或并行**：会把两层结构扩成递归图，增加工具定位、建检顺序与 TUI 复杂度；当前真实需求只需扁平严格串行阶段。
- **归档纯 Work List 或完整 mutation log**：会把 `/dgoal s` 扩成通用工作日志，偏离只追溯 Plan Run 的目标。
- **跨 session 项目账本或历史恢复**：会形成多目标池与恢复语义，超出会话内单 Goal 边界。
