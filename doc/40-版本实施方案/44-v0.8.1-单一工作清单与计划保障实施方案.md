# v0.8.1 单一工作清单与计划保障实施方案

> Status：实现完成，自动化与发布验收收尾中。受 ADR 0051 与项目路线图约束；本文件继续作为 v0.8.1 产品行为与验收权威，真实模型 / TUI 状态按最终验证结果单独报告。

## Problem Statement（问题陈述）

当前三档 Plan 统一在 `goal → phase → task` 数据形状上。Task Plan 为复用这套结构必须制造隐藏 phase；只做 goal 终审的 Phase Plan 也必须创建显式 phase。普通多步工作因而无法先使用跨 turn 保留但不自动续跑的轻量 Work List，Plan 的结构层级、持续执行合同和独立建检密度被同一个 `planType` 同时决定。

这些耦合已经扩散到公共工具、持久化校验、prompt、恢复、状态守卫、持续浮层、`/dgoal s` 和测试夹具。继续在现有结构上增加“可选 phase”或“计划内外清单”只会形成更多分支，不能删除隐藏 phase 根因。与此同时，终态 Plan 清空后没有用户可查询的 Plan Run History，完成、清理和替换过的计划无法在当前 session 回看。

## Solution（解决方案）

v0.8.1 以当前 Goal 下唯一 Work List 作为统一工作底座。普通多步工作先建立软性 Work List；它跨 turn 保留但不自动续跑。需要更强保障时，在同一个 Goal 和同一张 Work List 上建立或单向升级 Plan Contract：Execution Plan、Goal Check Plan、Staged Check Plan。

Phase 变为同一 Work List 内按真实阶段边界建立的可选组合节点，不承担直接工作、不嵌套、严格串行并始终显式收口。Execution / Goal Check 不强制 Phase；Staged Check 因逐阶段审核必须至少有一个真实 Phase。终态 Plan Run 以裁掉原始审核报告的结构化快照进入当前 session History；纯软性 Work List 和逐项修改日志不归档。

本版本以新的公共工具面与持久化世代一次性切换，删除旧隐藏 phase 路径、旧五个 Plan 管理/建立工具和旧活动状态读取，不保留生产双轨。

## User Stories（用户故事）

1. 作为普通 Pi 用户，我希望 agent 能先建立一张轻量工作清单，让多步工作跨回合可见，但不会因为列了清单就自动持续运行。
2. 作为需要无人值守完成的用户，我希望 agent 能把当前清单升级为执行计划，持续推进并显式收口，而不制造我看不见的阶段。
3. 作为要求独立终审的用户，我希望在确认后把同一工作升级为目标建检计划，即使真实工作没有阶段也能运行 `goal_check`。
4. 作为要求逐阶段保障的用户，我希望确认真实阶段及其验收条件，逐阶段建检后再做目标终审。
5. 作为查看进度的用户，我希望持续浮层始终只展示同一张清单的当前投影，并能在 `/dgoal s` 的 Current / History 视图查看当前工作和当前 session 的终态计划。
6. 作为恢复会话的用户，我希望 Work List、活动 Plan Contract 与 Plan Run History 在 turn、session compact、session tree 和同一 session 恢复后保持一致。
7. 作为维护者，我希望删除隐藏 phase 及其特殊校验、提示和测试，不再维护新旧数据结构或工具别名双轨。

## Confirmed Constraints（已确认约束）

### 1. Goal 与唯一 Work List

- 同一 Pi session 同时最多有一个当前 Goal。
- Goal 必须有非空 objective 与 Description，并且只拥有一张逻辑 Work List。
- Work List 是 Work Item、Phase、依赖、状态和当前投影的唯一数据源；不存在计划内外多清单或条目级 Plan 豁免。
- 软性 Work List 没有 Plan Contract。未完成内容跨 turn 保留，但 agent turn 结束时不得发送 synthetic continuation。
- 软性状态允许 agent 按证据整份重写、拆分、合并、删除和重排 Work Item；清单项可以先是模糊或复合候选。
- 软性 Goal 的全部 Work Item 终结后可显式关闭或清除，但不产生 Plan Run History。

### 2. Work Item 与 Description / Evidence

- Work Item 至少有稳定 ID、subject 与状态；软性状态下 Description、evidence 与 deliverables 可省略。
- Work List 进入任一 Plan Contract 前，agent 必须原子归一当前快照：所有保留的计划态 Work Item 具有非空 Description；done 项具有可复验证据；声明 deliverables 的 done 项具有逐项 deliverableEvidence；abandoned 项具有明确原因。
- 计划态 Work Item 使用 `pending → in_progress → done | blocked | abandoned`。done 与 abandoned 都是终态；done 不回退，后续缺陷用 follow-up Work Item；blocked 解除后回到 in_progress。
- abandoned 不提供完成证据，也不能满足已声明 deliverable；主 agent 的 Phase / Goal 收口比较和独立审核仍可因放弃造成的真实缺口拒绝完成。
- `blockedBy` 继续使用 plan-global Work Item ID、禁止环，并不得通过依赖绕过严格 Phase 顺序。
- Phase 与 Work Item 使用类型化引用及各自从 1 开始的编号；Work Item ID 在整张 Work List 内唯一，不按 Phase 重置。

### 3. Phase 结构与完成

- Work List 顶层可以包含普通 Work Item 与 Phase；Phase 只包含普通 Work Item，不允许 Phase → Phase 或任意深度内容树。
- 多个 Phase 按当前 Work List 中的确认顺序严格串行；前一 Phase 未显式 done 时，后一 Phase 的工作不可进入执行前沿。
- Execution Plan 与 Goal Check Plan 的 Phase 可选；Staged Check Plan 必须至少有一个真实 Phase。
- Staged Check Plan 激活时，所有尚未终结的 Work Item 必须归入某个 Phase；升级前已经终结的前置工作可以作为同一 Work List 的历史事实保留。
- Phase 必须有 subject 与 Description。Staged Check Plan 的每个 Phase 还必须有冻结的独立验收条件。
- Phase 成员工作耗尽只产生“等待收口”前沿。主 agent 必须先判断是否新增或重组 Work Item；所有保障档位都通过显式 `work_update` 写 Phase done。
- Staged Check Plan 还要求当前 Phase revision 的 `phase_check=approved`；check 只记录结论，不能代写 done。
- Staged Check Plan 的 Phase 主干与验收条件在确认后冻结；运行中不新增、删除、嵌套或重排 Phase。Execution / Goal Check 的 Phase 属于 agent 组织结构，变化会递增 revision 并使适用的旧 goal check 失效。

### 4. Plan Contract 与单向升级

Work List 本身不是 Plan。Plan Contract 使用固定三档：

| Profile | Until Done | goal_check | phase_check | Phase | 激活所有权 |
|---|---:|---:|---:|---|---|
| Execution Plan | 是 | 否 | 否 | 可选 | agent |
| Goal Check Plan | 是 | 是 | 否 | 可选 | 用户显式确认 |
| Staged Check Plan | 是 | 是 | 是 | 必需 | 用户显式确认 |

- 从软性 Work List 首次进入任一 Profile 时创建 Plan Run ID、planStartedAt 与初始 revision。
- 同一 Plan Run 只允许 `Execution → Goal Check → Staged Check` 单向升级；沿用 Goal、Work List、Plan Run ID 与 planStartedAt，并记录 profile transition。
- Goal Check / Staged Check 的建立和升级继续经过真实用户显式授权、语义预审和确认 UI；agent 不能自行提高到独立建检档位。
- 降低保障必须先由用户显式结束或清理当前 Plan，再建立新的 Plan Run；不得在原运行中撤销 acceptance contract。
- Goal Check 确认后冻结 Goal objective、Description、goal acceptanceCriteria、nonGoals 与 guardrails。升级 Staged Check 时保留上述 Goal 契约，并新增冻结的 Phase 主干与 Phase acceptanceCriteria。
- Execution Plan 的 Goal 与工作组织仍可由 agent 按新证据显式修订；真实用户意图已经改变时，旧 Plan Run 必须以 superseded 归档，而不是把新目标伪装成同一修订。

### 5. 完成链与自动续跑

- 软性 Work List 不启动 continuation、活性计数或 Until Done 收口守卫。
- Plan Contract active 时复用结构化 continuation 与双层 no-progress 熔断；运行时不解析 assistant 文本、命令字符串或源码语义。
- Work Item 状态/evidence/blocked/集合、Phase/Goal 状态、Profile 升级、成功文件写入及独立 check 终态属于结构化持久进展；只读、失败写入、无终态 check 与仅改自由文本继续只算 activity。
- Execution Plan：当前工作耗尽后，主 agent新增/重组工作，或回读 Work Item Description、证据与显式交付物后，以 summary / verification 显式关闭 Goal。
- Goal Check Plan：真实 Phase（如有）逐个显式关闭；全部 Work Item 终结、全部 Phase done 后运行 goal_check，当前 revision approved 后显式关闭 Goal。
- Staged Check Plan：每个 Phase 按“工作耗尽 → 主 agent 比较 → phase_check → 显式 Phase done”推进；全部 Phase done 后 goal_check，approved 后显式关闭 Goal。
- 全部 Work Item 必须 done 或 abandoned 才能关闭 Goal；blocked / pending / in_progress 均不放行。
- 用户中断 Execution Plan 只停止当前响应并保留 active；下一条真实用户输入可继续。Goal Check / Staged Check 的用户中断继续进入显式 paused / resume 边界。
- Execution Plan 的 no_progress 与 model_error 保留 ADR 0049 / 0050 的受限恢复原则；高保障 Profile 不自动借真实用户输入解除显式暂停。

### 6. 九个公共工具

v0.8.1 注册且只注册以下九个两词工具：

| 工具 | 公开责任 |
|---|---|
| `work_list` | 建立或整份重写软性 Goal / Work List；活动 Plan Contract 下拒绝无痕整单替换 |
| `execution_plan` | 直接建立 Execution Plan，或把当前软性 Work List 原子归一并升级；无需用户确认 |
| `goal_plan` | 提交 Goal Check Plan 或把当前软性 / Execution Plan 升级为 Goal Check，经语义预审和用户确认 |
| `staged_plan` | 提交 Staged Check Plan，或把较低 Profile 升级为 Staged Check，经语义预审和用户确认 |
| `work_create` | 新增 Work Item；允许的 Profile 下可新增真实 Phase，Staged Check 确认后不得新增 Phase |
| `work_read` | 读取当前 Goal、完整 Work List、Phase、Work Item 或 Plan Run History；paused 下仍可用 |
| `work_update` | 唯一 agent 状态写入口：更新 Work Item、显式关闭 Phase / Goal、记录证据/依赖/放弃原因及结构化暂停 |
| `phase_check` | 仅 Staged Check Plan 审核当前 Phase，写 CheckRecord，不写 done |
| `goal_check` | Goal Check / Staged Check Plan 审核 Goal，写 CheckRecord，不写 done |

- 工具名继续不使用 `dgoal_` 前缀，并保持严格参数模式可兼容的 schema。
- 旧 `task_plan`、`phase_plan`、`plan_create`、`plan_read`、`plan_update` 不注册、不保留 alias；旧 `goal_plan` 的 Phase + Goal 双审语义由 `staged_plan` 承接。
- 工具结果继续提供紧凑摘要与人类可读展开，不把原始 details 直接渲染给用户。
- `work_read` / `/dgoal s` / 主 agent prompt 共享同一个当前前沿和依赖图纯读模型。

### 7. 启动闸门

- 默认 guidance 从“普通多步直接建立 Task Plan”改为“先建立软性 Work List；只有需要持续完成时由 agent 升级 Execution Plan”。纯讨论、解释、单步回答与必须由用户决定的问题仍不机械建清单。
- `/dgoal` 与真实用户明确要求启动 dgoal 时，主 agent在 Goal Check Plan / Staged Check Plan 之间推荐；Execution Plan 不进入该确认框。
- 确认 UI 展示 Goal、完整 Work List、Profile、Goal 契约；Staged Check 额外展示 Phase 与 Phase 契约。用户可确认、拒绝、反馈或要求切换两种高保障 Profile。
- proposal 在结构、授权与语义预审成功前不得改变活动 Work List 或启动 Plan Run；已有软性 / Execution 状态只在用户确认后原子升级。
- 人工体验继续进入 userReviewItems，不进入独立完成门；审核器不得扩张冻结契约。

### 8. 持久化与兼容

- 当前状态使用 `dgoal-work-v1` custom entry，last-write-wins 保存当前 Goal、唯一 Work List、活动 Plan Contract 与 pending proposal。
- 终态历史使用独立的 `dgoal-plan-history-v1` custom entry，只有 Plan 终结或历史删除时追加新的完整 History snapshot，避免每次 Work Item 更新重复写入全部历史。
- load guard 严格验证单 Goal / 单 Work List、非嵌套 Phase、严格 Phase 顺序、类型化 ID、依赖无环、Profile 单向变更、Description / evidence / acceptance contract、revision / CheckRecord 与已删除旧字段。
- `dgoal-plan-v2` 及更早 key 不读取、不迁移、不展示，也不建立兼容工具或状态机；发布说明必须标明旧活动状态需要重新建立。
- session start / tree / compact 从当前 branch 分别恢复最新 Work state 与 History snapshot；旧 generation 的 check 与 continuation 不得写回新分支。
- Plan 终结时必须先形成去重的终态历史记录并落盘，再清理活动状态；重放或 UI 异常不得丢失历史、重复归档或复活 Goal。

### 9. Plan Run History 与 `/dgoal s`

- History 只包含进入过 Plan Contract 的 `done | cleared | superseded` 等终态 Plan Run；纯软性 Work List 不归档。
- 同一次运行中的 Profile 升级保存在一条记录中，不拆分历史。
- 每条记录包含 Goal、最终 Work List 结构、Profile transitions、起止时间、终态原因、summary / verification、交付物证据、Phase / Goal Check 的状态、模型、时间与 revision。
- 归档时裁掉原始 auditor report、thinking、完整 transcript、逐工具 checkpoint 正文和 Work Item mutation log；活动 Plan 中用于修复的 rejected feedback 不因归档边界反向扩张 History。
- `/dgoal s` 使用 `Current（当前）` / `History（历史）` 顶层视图。没有当前 Goal 且存在历史时默认打开 History；历史列表按结束时间倒序，Enter 打开只读详情。
- `/dgoal clear` 对活动 Plan 写 `cleared` 历史后清除；软性 Work List 直接清除且不归档。
- 新增独立、需确认的 `/dgoal history clear`，只删除当前 session 的 Plan Run History，不影响活动 Goal / Work List。
- History 不可 resume、clone 或改回 active，不形成跨 session 项目账本。

### 10. TUI 与可见性

- 持续浮层始终投影唯一 Work List，不创建计划层与清单层双浮层。
- 软性 Work List、Execution Plan 默认展示当前 Work Item；存在真实 Phase 时按 Goal → Phase → Work Item 层级投影。保障 Profile 只在 heading / 状态提示中表达，不复制工作树。
- active 浮层继续最多 10 行，优先保留当前/未完成工作；完成快照与 History 详情不受日常折叠策略冒充。
- `/dgoal s` Current 继续支持 Goal Description、前沿、逻辑项选择、详情滚动与返回保位；History 复用同一 Modal 的顶层 tab，不增加第二个状态命令。
- TUI 仍是 after-effect。持久化、Profile 升级、CheckRecord、Phase / Goal 完成、历史归档与清理必须先于并独立于任何 widget、status、notify 或 Modal 更新。

## Acceptance Criteria（验收标准）

### Work List 基线

- [x] 普通多步任务可由 `work_list` 建立单 Goal / 单 Work List；未完成条目跨真实 turn 和 session compact 保留，agent turn 结束不触发 continuation。
- [x] 软性 Work Item 可缺少 Description / evidence，并可被整单重写；当前状态始终只有一张 Work List，代码、工具结果、prompt 与 TUI 都不存在计划内外双清单。
- [x] Work List 为空或全部终结时可显式关闭/清除软性 Goal，且不会产生 Plan Run History。

### Plan Contract 与升级

- [x] `execution_plan` 能直接建立或升级当前 Work List；升级后自动续跑和完成守卫生效，且没有任何隐藏 Phase。
- [x] Goal Check Plan 可在零 Phase 的平铺 Work List 上经用户确认运行完整 `goal_check → work_update(goal, done)` 链。
- [x] Staged Check Plan 拒绝零 Phase、嵌套 Phase、并行越序和未归入 Phase 的非终态 Work Item，并跑通 `phase_check → explicit phase done → goal_check → explicit goal done`。
- [x] Execution → Goal Check → Staged Check 沿用同一 Plan Run ID / startedAt 并记录 transitions；任意反向降级被拒绝。
- [x] Goal Check / Staged Check 未经真实用户授权、语义预审或确认不能激活；失败 proposal 不改变现有软性 / Execution 状态。

### 状态与守卫

- [x] 所有真实 Phase 在成员工作耗尽后仍保持等待收口；Execution / Goal Check 需要显式 Phase done，Staged Check 还需要当前 Phase revision approved。
- [x] done Work Item 必须满足 evidence / deliverableEvidence；abandoned 必须有原因且不能冒充 deliverable 完成；任何未终结 Work Item 都阻止 Goal done。
- [x] `phase_check` / `goal_check` 只写 CheckRecord；`work_update` 是 Phase / Goal done 的唯一 agent 工具入口，旧 approval 在相关 revision 变化后失效。
- [x] Staged Check 的 open Phase 不能被 root Work Item 绕过；全部 Phase done 后可新增由 goal 终审覆盖的 root follow-up，且该状态可恢复。Phase local facts 变化会失效 phase check，done Phase 不回退或改写。
- [x] soft Work List 不计 no-progress；三档 Plan 继续覆盖 3 轮无工具、8 轮只有 activity、真实 durable progress 清零及 start/resume/resync/clear/finalize 隔离。
- [x] Execution Plan 的模型错误真实用户输入恢复与 no-progress 受限恢复保留；高保障 Plan 不被 extension 输入或普通用户输入自动解除显式暂停。

### 工具与破坏性切换

- [x] RPC 与真实宿主只注册九个新工具；五个被删除工具完全不可见，且 `goal_plan` / `staged_plan` 的新审核责任与文档一致。
- [x] 新工具在支持 strict schema 的模型上可调用，在不支持时由宿主正常回退；nullable 参数不会被错误转换成有效 ID 或状态值。
- [x] 代码、测试、prompt、i18n、README、帮助文本与 smoke driver 中不存在隐藏 Phase、旧三档名称或旧工具专属活路径。

### 持久化与历史

- [x] `dgoal-work-v1` 能严格往返软性、三档 Plan、Profile transitions、Phase / Work Item、暂停与 pending proposal；旧 `dgoal-plan-v2` 被忽略且不能越过启动闸门。
- [x] done、cleared、superseded 各产生一条去重的 session History；Profile 升级不拆记录，纯软性 Work List 不产生记录。
- [x] History 在 turn、session compact、session tree 与同一 session 恢复后可见；独立新 session 不继承。
- [x] 归档记录包含最终结构与 Check 元数据，但不包含 auditor report / thinking / transcript / mutation log。
- [x] `/dgoal clear` 不删除既有 History；`/dgoal history clear` 经确认后只清空 History，不影响活动 Work List。

### TUI 与失败边界

- [x] 持续浮层只显示一张 Work List，active 最多 10 行；平铺和真实 Phase 层级、软性/三档 heading、完成与折叠投影可由纯渲染测试复验。
- [x] `/dgoal s` 的 Current / History 顶层导航、默认 tab、终态倒序、只读详情、滚动、返回保位与无当前 Goal 边界均有确定性测试。
- [x] 模拟 widget、status、notify、确认 UI、History Modal 抛错时，Work List / Plan / Check / History 的内存与持久化事实仍正确，终态 Goal 不复活。

### 验证入口

## Vertical Slices（垂直切片）

### 切片 1：软性 Work List 基线

交付单 Goal / 单 Work List 纯数据模型、软性 Work Item 生命周期、新持久化 current-state 世代、`work_list` / `work_create` / `work_read` / `work_update` 的软性路径，以及单清单浮层和跨 turn / compact 恢复。完成信号是普通多步工作可结构化保留但绝不自动续跑；旧 Plan 生产路径尚不能切入新状态。

### 切片 2：Execution Plan Until Done

在同一 Work List 上交付 `execution_plan`、计划态结构归一、Description / evidence / deliverable 守卫、显式 Goal 收口、continuation、双层 no-progress 与 Execution 专属恢复。完成信号是无 Phase 的平铺执行计划可端到端持续完成，且 Task Plan 隐藏 Phase 不进入任何新数据或投影。

### 切片 3：Goal Check Plan

交付 `goal_plan` 的显式授权、原子 proposal / confirmation、零 Phase 可用的 Goal acceptance contract、goal_check / update 分离及 Execution → Goal Check 同运行升级。完成信号是平铺 Work List 能经独立目标终审关闭，失败 proposal 与 rejected 修复不破坏原状态。

### 切片 4：真实 Phase 与 Staged Check Plan

交付非嵌套严格串行 Phase、所有 Profile 的显式 Phase 收口、`staged_plan`、Phase acceptance contract、局部 revision、phase_check 和 Goal Check → Staged Check 同运行升级。完成信号是无隐藏容器的真实阶段双层建检链可端到端通过，并覆盖越序、脏依赖与迟到审核失败路径。

### 切片 5：Plan Run History 与状态面板

交付终态 History 持久化、去重归档、Current / History Modal、终态详情、`/dgoal clear` 归档语义与 `/dgoal history clear` 确认。完成信号是当前 Goal 清空后仍可在同一 session 回看结构化 Plan Run，且没有原始审核报告或恢复入口。

### 切片 6：破坏性切换与全链路清理

删除旧五工具、隐藏 Phase、旧 `PlanType` / `TaskPlan.phases` 特判、旧持久化读取、旧 prompt / TUI / i18n / 测试夹具与文档路径；同步 package、README、CHANGELOG、架构文档、术语表、路线图和 smoke。完成信号是仓库只有新单路径，旧 key 仅出现在兼容拒绝测试、历史 ADR 与 CHANGELOG 中。

## Out of Scope（非目标）

- 多 Goal 池、跨 session 历史汇总、项目级运行账本、后台 daemon、scheduler 或定时触发。
- Plan Run History 的恢复、克隆、继续执行或完整 Work Item mutation log。
- 原始 auditor report、thinking、完整 transcript 或逐工具 checkpoint 的历史浏览。
- 多张 Work List、计划内外分栏、Work Item 级 Plan 豁免或双层持续浮层。
- Phase 嵌套、Phase 并行、任意深度内容树或运行中为 Staged Check 静默新增 Phase。
- 自由组合 goal / phase check 开关；只提供三档固定保障预设。
- 迁移或只读展示 `dgoal-plan-v2` 活动状态，及旧工具 alias / deprecated 双轨。
- 自动 Git commit、push、发布、部署、远端写入或替代项目自身测试命令。

## Further Notes（补充说明）

- 本版本是明确的破坏性升级。代码、`doc/10-架构与运行/`、README、术语表、路线图与测试地图已整体切换为 v0.8.1 当前事实；历史行为只在 ADR、CHANGELOG 与拒绝回归中追溯。
- 实现按软性 Work List → Execution → Goal Check → Staged Check → History 垂直生长，并在切换阶段删除旧生产路径；当前没有永久适配层或双写状态。
- Plan Run History 增加 session 体积，但本版本不预设跨 session 保留期或项目级索引；只通过终态快照、独立 History 写入和裁掉报告正文控制增长。
- 任何实现中发现会改变“单 Work List、Profile 单向升级、真实 Phase、显式完成、历史只读”产品语义的问题，必须返回 ADR 0051 / 本规格修订，不能在代码层静默另定规则。
