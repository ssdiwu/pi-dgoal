# pi-dgoal 术语表

pi-dgoal 是一个 Pi 扩展：同一 session 当前 Goal 只拥有一份 Work List；普通工作可保持 soft（软性），需要时在同一清单上附加 Execution / Goal Check / Staged Check Plan Contract。ADR 0051 是 v0.8.1 当前术语权威。

## 核心对象

**Goal（目标）**：
同一 Pi session 当前唯一的工作方向、生命周期与组织根。它拥有且只拥有一份 Work List；`objective` 是短标题，`description` 说明理由、作用与方法边界。
_Avoid_：把 Goal 当作第二张工作清单；同时维护多个 current Goal

**Work List（工作清单）**：
当前 Goal 唯一拥有的结构化工作集。它可以 soft 跨 turn 保留，也可在不换清单的前提下进入 Plan Contract。
_Avoid_：同一 Goal 拆成计划内/计划外两张清单；把 Work List 本身等同于 Until Done

**Work Item（工作项）**：
Work List 的直接工作单元。ID 在整份 Work List 内唯一；可位于根层或一个真实 Phase 内。soft 时 Description / evidence 可省略；计划态必须有 Description，done 必须有 evidence。
_Avoid_：继续称为旧 Task；预先穷尽所有步骤；把主观用户验收写成 evidence

**Phase（阶段）**：
Work List 中可选的真实串行边界。Phase 不直接承担工作，只包含 Work Item；不得嵌套，多个 Phase 严格串行，成员耗尽后仍须显式完成。
_Avoid_：隐藏 Phase；按代码/测试/文档等横向工作面机械拆 Phase；成员耗尽即自动 done

**Description（执行说明）**：
回答“为什么存在、如何服务上层、为何采用当前方法、要避免何种方法偏移”的耐久文本。Goal、真实 Phase 与计划态 Work Item 必填；soft Work Item 可省略。Description 是执行指导，不是独立完成门。
_Avoid_：复述标题；写实时进度或 transcript；从 Description 临时扩张 acceptance gate

**Deliverable（交付物）**：
Work Item 可选的 `{ target, description }` 声明。声明后，done 时 `deliverableEvidence` 必须与每个 target 一一对应；通用 `evidence` 仍描述 Work Item 整体完成事实。

**blockedBy（依赖）**：
引用 plan-global Work Item ID 的有向无环依赖。可引用根层、同 Phase 或更早 Phase 的 Work Item；较早 Phase 不得依赖未来 Phase。

## 保障与生命周期

**Plan Contract（计划合同）**：
附着于当前 Goal + Work List 的 Until Done / 独立建检保障。它不创建第二张清单；Profile、revision、验收契约、审核记录和暂停状态都属于这条保障生命周期。

**Soft Work List（软性工作清单）**：
没有 Plan Contract 的 Work List。跨 turn 保留，但不启动 continuation、no-progress 计数或独立审核。全部 Work Item terminal 且所有真实 Phase 显式 done 后自动清理并返回完成总结。

**Execution Plan（执行计划）**：
agent 可主动建立的 Until Done Profile。持续推进、启用固定技术熔断并显式关闭 Goal，但没有独立 check；Phase 可选。

**Goal Check Plan（目标建检计划）**：
必须经用户显式授权和确认；在 Until Done 上增加 goal 独立终审。可以完全平铺，也可有真实 Phase；Phase 不携带 acceptanceCriteria，不调用 `phase_check`。

**Staged Check Plan（分阶段建检计划）**：
必须经用户显式授权和确认；至少一个真实 Phase，每个 Phase 有独立 acceptanceCriteria，并在最终 goal 终审前逐 Phase 建检。

**Assurance Upgrade（保障升级）**：
同一 Plan Run 内单向提高保障：`execution → goal_check → staged_check`。升级保留 Goal、Work List、Plan Run ID、startedAt、终态与证据；不得降级。

**Until Done（直到完成）**：
Plan Contract active 时，agent 在当前 session 内通过 continuation 持续推进，直到显式完成、清除、被取代或进入 paused。它不是跨 session daemon、scheduler 或后台任务。

**Plan Run（计划运行）**：
Work List 首次进入 Plan Contract 时开始，在 `done | cleared | superseded` 终态结束的一次连续保障生命周期；Profile 升级不切分新 Run。

**Plan Run History（计划运行历史）**：
当前 session 分支内终态 Plan Run 的只读 append-only 快照。保留结构化 Work List、验收条件、check 结论、summary / verification / whatChanged / userReview；不保存 auditor report、feedback、thinking、transcript 或 mutation log，也不能恢复为 active。

## 建检与证据

**Build-Check Loop（建检循环）**：
先建造，再由 fresh context 的独立审核器核验冻结条件；不通过就继续修，通过后仍由 `work_update` 显式完成。Goal Check 在 goal 层应用；Staged Check 在 Phase + goal 两层应用；soft / Execution 不启用独立审核。

**Acceptance Criterion（独立验收条件）**：
`{ criterion, evidence }` 结构，必须能由审核器通过项目工件、受限命令或可观察外部状态独立复验。主观体验与人工偏好不属于机器完成门。

**Verification（全局验收说明）**：
帮助用户和 agent 理解整体完成标准的文字；Goal Check / Staged Check proposal 必填，但不替代结构化 acceptanceCriteria。

**User Review（用户复核）**：
完成后交由用户体验、观察或偏好判断的非阻塞事项。它不得被报告成已经自动验证。

**CheckRecord（审核记录）**：
一次 Phase 或 Goal 独立审核的结构化事实：`approved | rejected | audit_error`、modelId、checkedAt、revision，可在 active 状态下存在；不是完成状态。

**Check / Update 分离**：
`phase_check` / `goal_check` 只写 CheckRecord；`work_update` 才能写 Phase / Goal done 与完成显示。approved 不等于 done，check 也不得要求 done 预先存在。
_Avoid_：在 check 内顺手完成；把 `work_update` 当成绕过审核的后门

**Semantic Preflight（语义预审）**：
Goal Check / Staged Check 写 pending proposal 前，由当前会话模型检查验收条件是否可自主闭环，迁移 subjective 条件到 `userReviewItems`，并拒绝依赖凭据、授权、用户决策或未来审核器拿不到的历史证据。技术失败与语义拒绝分开返回。

**Thin Proposal, Hard Execution（轻提案、硬执行）**：
代码管结构、状态与授权；LLM 管 proposal 语义；真实动作仍受宿主权限和执行边界约束；独立审核器只核确认后冻结条件。

**Audit Candidate Chain（审核候选链）**：
Phase / Goal scope 各自最多三个有序模型候选。只在技术或协议失败时切换，不因业务 rejected 换模型；健康候选在同 scope 复用，全部耗尽后进入 `paused(audit_error)`。

**Audit Checkpoint（审核检查点）**：
按 scope 与 workspace fingerprint 保存的脱敏成功工具事实。逐工具运行态只在内存；稳定终态才能持久化复用。工作区变化、失败、unknown 或 running 记录都不能作为完成证据。

## 九个公共工具

工具名遵循两词规则，不带 `dgoal_` 前缀。

### 建立与升级

- **`work_list`**：创建或原子重写 soft Work List；不启动自动续跑。
- **`execution_plan`**：直接建立 Execution Plan，或原子把同一 soft Work List 归一为计划态。
- **`goal_plan`**：提交 Goal Check Plan proposal；允许零 Phase，不做 phase check。
- **`staged_plan`**：提交 Staged Check Plan proposal；必须至少一个真实 Phase，每 Phase 有 acceptanceCriteria。

### 管理与读取

- **`work_create`**：新增 Work Item；当前 Profile 允许时新增真实 Phase。Staged Check 确认后 Phase 主干冻结。
- **`work_read`**：只读查询当前 Goal / Work List / Phase / Work Item 或 session Plan Run History；paused 时仍可用。
- **`work_update`**：唯一 agent 状态写入口；更新 Work Item，显式完成/阻塞 Phase，暂停 Plan Contract，或完成 Goal。

### 独立建检

- **`phase_check`**：只用于 Staged Check 的当前 Phase，记录 Phase local revision 的 CheckRecord。
- **`goal_check`**：用于 Goal Check / Staged Check 的完整 Goal，记录 Work List revision 的 CheckRecord。

## 状态机

**Goal status**：`pending | active | paused | done`

- `pending`：高保障 proposal 正在预审或等待确认。
- `active`：soft Work List 或 Plan Contract 正在推进。
- `paused`：只适用于 Plan Contract；continuation 停止，等候恢复或用户处理。
- `done`：完成事实会先持久化，随后写 null tombstone 清除 current Goal。

**Work Item status**：`pending | in_progress | done | blocked | abandoned`

- `done` / `abandoned` 是 terminal（终态），都不回退。
- 计划态 `done` 必须有 evidence；声明 deliverable 后还需逐项证据。
- `blocked` 必须有 `blockedReason`；`abandoned` 必须有 `abandonedReason`。

**Phase status**：`pending | in_progress | done | blocked`

- 多 Phase 严格串行，后续 Phase 不能越过当前未 done Phase。
- Phase 成员耗尽不自动完成；`work_update(target=phase,status=done)` 是唯一完成入口。
- Staged Check Phase done 还要求当前 local revision approved。

**Paused（暂停态）**：
固定原因为 `user_abort | model_error | audit_error | no_progress | agent_blocked`。soft Work List 不进入 paused。Execution 的 model_error 可由与当前 Goal + 原 prompt 精确绑定的真实 interactive/RPC 输入一次性恢复；extension 注入与改写 prompt 不授权。其他 Profile / 原因通常需显式 `/dgoal resume`。

**Revision（修订号）**：

- `WorkList.revision` 对所有持久写单调增加，保护 goal_check 与 Plan Contract snapshot。
- `WorkPhase.revision` 只在所属 Phase 的受审说明等 local fact 变化时增加，保护 phase_check；无关 Phase 不使其失效。
- 审核期间若 session generation、Goal ID 或相关 revision 改变，迟到结果丢弃。

**Terminal closure（终态关闭）**：
完成顺序固定为：写 Goal done → 写 null tombstone → 取消 continuation → 清 proposal、熔断计数、check snapshot、授权与恢复 token → 清状态栏 → done snapshot 后隐藏。所有 Profile 返回用户可见 `dgoal 完成信号`。

## TUI 与上下文投影

**Persistent Widget（持续浮层）**：
Pi `setWidget(..., placement:"aboveEditor")` 的常驻面板。显示 Profile、聚合 Work Item 进度、真实 Phase 与当前 frontier；`Ctrl+O` 展开 Work Item 与审核活性。

**Status Modal（详细查询 Modal）**：
`/dgoal s` 打开的列表/详情 overlay。Current tab 浏览 Goal、Phase、Work Item；History tab 浏览 Plan Run。详情展示 Description、status、dependency、evidence、reason、deliverable 与适用 CheckRecord。

**Soft Forgetting（软遗忘）**：
done Phase 在主 agent 每轮执行上下文只保留标题，成员、Description、evidence 与 acceptanceCriteria 不再持续占用 prompt；结构化持久态、TUI 与 History 仍保留完整耐久事实。

**Fail-soft TUI（失败降级 TUI）**：
状态写入、持久化、审核与渲染分离。`setWidget`、Modal、status、notify 或 done snapshot 抛错只能影响展示，不能回滚或阻断 Goal 生命周期。

## 持久化与活性

**Current-state key（当前态键）**：
`dgoal-work-v1`。保存唯一 current Goal、Work List、可选 Plan Contract 与 pending proposal；last-write-wins，并以 null tombstone 表示无 current Goal。

**History key（历史键）**：
`dgoal-plan-history-v1`。保存当前 session 分支的 Plan Run History；先持久化再替换内存列表，按 Plan Run ID 去重。

**Breaking isolation（破坏性隔离）**：
v0.8.1 之前的活动状态不读取、不迁移、不显示、不恢复。旧结构和工具名只允许出现在历史 ADR / CHANGELOG 与明确的拒绝回归测试中。

**Plan priority after compaction（压缩后计划权威）**：
`session_compact` 恢复严格校验的 Work List / Plan Contract。结构化状态是执行与收口权威；压缩摘要只能补背景。Plan Contract active 且 Pi 未 retry 当前 turn 时重新投递 continuation；soft Work List 不投递。

**Structured Liveness Detection（结构化活性判定）**：
只在 Plan Contract active 时观察工具 activity 与 durable progress。运行时不解析 assistant 文本、shell 命令或源码语义；持续停滞达到固定阈值后进入 `paused(no_progress)`。

**Durable Progress（持久进展）**：
可跨轮观察并复验的结构化结果，例如成功文件写入、Work List status/evidence/dependency/集合变化，或独立 check 的 approved/rejected 终态。只读查询、失败写入、无终态 check、仅改标题/Description 与 no-op 只算 activity。

**Fixed circuit breakers（固定技术熔断）**：
模型连续错误、3 轮无工具、8 轮只有 activity 无 durable progress、审核器故障/timeout、用户中断与 agent blocker。它们是可靠性边界，不是用户可配置 runtime budget。
