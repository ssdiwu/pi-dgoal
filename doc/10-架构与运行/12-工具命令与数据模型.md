# 12 - 工具、命令与数据模型

> 当前权威：ADR 0051。公共 agent 工具固定为九个两词名称；当前态键为 `dgoal-work-v1`，历史键为 `dgoal-plan-history-v1`。

## 工具矩阵

| 工具 | 主要参数 | 作用 |
|---|---|---|
| `work_list` | `objective`, `description`, root `items[]` 和/或真实 `phases[]` | 创建或原子重写 soft Work List |
| `execution_plan` | 同上；计划态 Work Item 必须有 Description | 建立/重组 Execution Plan，或升级 soft Work List |
| `goal_plan` | goal 契约 + 可选 flat items / phases | 提交 Goal Check Plan，进入语义预审与用户确认 |
| `staged_plan` | goal 契约 + 至少一个带 acceptanceCriteria 的 Phase | 提交 Staged Check Plan，进入语义预审与用户确认 |
| `work_create` | `target=item|phase` + subject / description / deliverables / blockedBy | 新增 Work Item；允许时新增真实 Phase；Staged 的 root follow-up 仅在全部 Phase done 后允许 |
| `work_read` | `target=list|goal|phase|item|history` + 可选 `id` | 纯读当前完整结构、Description、交付物/证据或 session Plan Run History |
| `work_update` | `target=item|phase|goal` + 状态、证据、原因、完成 review | 唯一 agent 状态写与完成入口 |
| `phase_check` | `phaseId` 或 `phaseNumber` | Staged Check 当前 Phase 独立审核；只写 CheckRecord |
| `goal_check` | `summary`, `verification` + 可选变更/风险包 | Goal Check / Staged Check 整体独立审核；只写 CheckRecord |

### `work_update` 目标

- `target=item`：更新 subject / description / status / evidence / deliverableEvidence / reason / blockedBy。soft 最后一个 terminal update 可能在同次调用自动关闭。
- `target=phase`：更新真实 Phase；done 要求全部成员 terminal，Staged Check 还要求当前 local revision approved。Phase 不自动 done。
- `target=goal,status=paused`：只允许 Plan Contract，且必须有具体 `reason`。
- `target=goal,status=done`：要求全部 Work Item terminal、全部 Phase done；Plan Contract 另要求 summary / verification，高保障 Profile 还要求当前 goal approval。

Staged Check 激活时所有非终态 Work Item 必须进入真实 Phase；运行中只要仍有 open Phase，新增 Work Item 也必须属于当前 Phase。全部 Phase done 后可追加 goal-level 根 follow-up，由后续 `goal_check` 覆盖，且不重开 done Phase。

### 关键不变量

1. 一个 session 只有一个 current Goal / Work List；公共工具和持久键是唯一写路径。
2. Work Item ID 在 Work List 全局唯一；Phase ID 使用独立 1-based namespace。
3. `blockedBy` 只能引用已存在 Work Item，不能成环，也不能从较早 Phase 指向未来 Phase。
4. `phase_check` / `goal_check` 不写 done；`work_update` 不能绕过当前 Profile 的审核守卫。
5. done 不回退；abandoned / blocked / paused 都必须有对应原因。
6. 计划态 Work Item Description 必填；done 必须有 evidence；声明 deliverables 后必须逐项留证。
7. Phase 永不因成员耗尽自动完成；Staged Check 确认后 Phase backbone 冻结。
8. soft Work List 不启动 continuation、no-progress 或独立审核；Plan Contract 才进入持续执行状态机。
9. Work List revision 单调递增；Phase local revision 与 goal revision 分别失效对应 check。
10. 关闭必须先写 done / tombstone 并清理全部运行态，再尝试 UI 后效；工具结果必须包含可见完成总结。

## 用户命令

```text
/dgoal <objective>       启动显式高保障，由 agent 推荐 Goal Check 或 Staged Check
/dgoal                   承接前文启动
/dgoal status | s        打开 Current / History 状态 Modal
/dgoal pause  | p        暂停 active Plan Contract
/dgoal resume | r        恢复 paused Plan Contract
/dgoal clear  | c        清除 current Goal / Work List
/dgoal history clear     二次确认后清空当前 session History
/dgoal help   | h        解释当前能力与状态
```

真实用户也可用明确祈使句要求使用 dgoal，复用同一显式启动闸门。soft / Execution 无需 `/dgoal`；但 `execution_plan` 不得静默承接已经授权的高保障请求。

## 核心数据模型

以下为当前类型的说明性投影；权威定义在 `src/work-list/index.ts` 与 `src/goal-runtime/types.ts`。

```ts
type GoalStatus = "pending" | "active" | "paused" | "done";
type WorkItemStatus = "pending" | "in_progress" | "done" | "blocked" | "abandoned";
type WorkPhaseStatus = "pending" | "in_progress" | "done" | "blocked";
type AssuranceProfile = "execution" | "goal_check" | "staged_check";

type AcceptanceCriterion = {
  criterion: string;
  evidence: string;
};

type WorkDeliverable = {
  target: string;
  description: string;
};

type WorkItem = {
  id: number;
  subject: string;
  description?: string; // soft 可省略；计划态必填
  status: WorkItemStatus;
  blockedBy?: number[];
  evidence?: string;
  deliverables?: WorkDeliverable[];
  deliverableEvidence?: Array<{ target: string; evidence: string }>;
  blockedReason?: string;
  abandonedReason?: string;
};

type WorkCheckRecord = {
  status: "approved" | "rejected" | "audit_error";
  report?: string;
  modelId?: string;
  checkedAt?: number;
  revision: number;
};

type WorkPhase = {
  id: number;
  subject: string;
  description: string;
  status: WorkPhaseStatus;
  revision?: number;
  items: WorkItem[];
  acceptanceCriteria?: AcceptanceCriterion[]; // 仅 Staged Check 冻结
  check?: WorkCheckRecord;
  feedback?: { report: string; createdAt: number };
  blockedReason?: string;
};

type WorkList = {
  items: WorkItem[];   // root-level items
  phases: WorkPhase[];
  nextItemId: number;
  nextPhaseId: number;
  revision: number;
};

type PlanContract = {
  id: string; // Plan Run identity
  profile: AssuranceProfile;
  startedAt: number;
  revision: number; // 必须等于 WorkList.revision
  transitions: Array<{ from?: AssuranceProfile; to: AssuranceProfile; at: number; revision: number }>;
  verification?: string;
  acceptanceCriteria?: AcceptanceCriterion[];
  userReviewItems?: string[];
  nonGoals?: string[];
  guardrails?: string[];
  goalCheck?: WorkCheckRecord;
  rejectedCount?: number;
  finalFeedback?: { report: string; createdAt: number; rejectedCount: number };
  auditorCandidates?: object;
  auditCheckpoints?: object;
  auditErrorScope?: "phase" | "goal";
};

type GoalState = {
  id: string;
  objective: string;
  description: string;
  status: GoalStatus;
  startedAt: number;
  updatedAt: number;
  iteration: number;
  workList?: WorkList;
  contract?: PlanContract;
  pauseReason?: "user_abort" | "model_error" | "audit_error" | "no_progress" | "agent_blocked";
  pauseReasonDetail?: string;
  pausedTotalMs?: number;
  pauseStartedAt?: number;
};
```

soft Goal 没有 `contract`。Execution Contract 不保存 acceptanceCriteria / goalCheck，Phase 也不保存独立条件。Goal Check 需要 goal verification + acceptanceCriteria，但 Phase 不带 criteria / check。Staged Check 还要求至少一个 Phase，且每个 Phase 有独立 criteria。

## Proposal 与升级原子性

`goal_plan` / `staged_plan` 只在以下边界内激活：

1. 当前 Goal 是 pending，或用户已显式授权为现有 Work List 升级保障。
2. 结构层归一并严格校验 planned Work List、Description、证据、Phase 顺序与依赖。
3. 语义预审保留未来审核器可独立取得证据的条件；主观体验迁移到 userReviewItems；真正缺凭据/授权/决策或依赖不可取得历史证据时拒绝。
4. 用户确认后才原子写入 Goal、Work List 与 Plan Contract；拒绝、预审技术失败、session 变化或 UI 失败不修改现有状态。
5. Goal Check → Staged Check 必须保留已冻结 Goal objective / description / acceptance contract，并把每个非终态 Work Item 归入真实 Phase。

Profile 不允许降级或同档 no-op 替换；Execution 重组仍保持同一 Plan Run，只有明确新目标取代时才归档旧 Run 为 superseded。

## 只读投影

`work_read` 与 `/dgoal s` 复用当前结构的纯派生视图：

- 当前 frontier、ready / waiting、直接依赖与根 blocker；
- Goal / Phase / Work Item Description、status、evidence、reason、deliverables；
- 只投影最新适用 CheckRecord 与 feedback，不展示内部修复历史；
- History 按 endedAt 倒序展示 Plan Run，详情只含脱敏耐久事实；
- 纯读不改变 revision、状态或 continuation。

## 独立审核器

`phase_check` / `goal_check` 共用 `src/audit/` 与 `src/isolated-pi/`。默认继承当前模型，也可配置最多 3 个 `provider/model[:thinking]` 候选。业务 rejected 不换候选；网络、协议、timeout、零输出等技术失败才回退。

审核 model idle timeout 为 180 秒，工具执行 idle timeout 为 1800 秒；phase / goal 共享候选总技术上限分别为 900 / 1800 秒。这些是固定可靠性参数，不是用户 runtime budget。

## 持久化

当前状态 last-write-wins：

```ts
api.appendEntry("dgoal-work-v1", { goal, pendingProposal });
```

Plan Run History 单独 append：

```ts
api.appendEntry("dgoal-plan-history-v1", { records });
```

- v0.8.1 之前的活动状态故意忽略，不迁移、不恢复。
- load guard 严格复验允许字段、Goal / Work List / Contract 组合、ID、状态、依赖、证据、transition、revision、check 与 pending proposal；任一脏字段拒绝整条 entry。
- `session_start` / `session_tree` / `session_compact` 重同步当前分支并增加内存 session generation；旧分支审核和 continuation 不能越界。
- compaction 后，active Plan Contract 在 Pi 未 retry 当前 turn 时投递新 continuation；soft Work List 只恢复状态，不自动续跑。

### History 裁剪

Plan Contract 以 done / cleared / superseded 终结时按 contract ID 去重归档。done 记录必须满足终态守卫；高保障 Profile 还要保留 approved goalCheck 的结构化结论。归档保留 Work List、criteria、check status/model/revision 与 completion review，删除 report、feedback、finalAuditHistory、checkpoint、candidate、thinking 和 transcript。History 不跨 session 分支继承，也不能转回 active。

## Evidence 与关闭边界

- planned Work Item done evidence 应指向可复验命令、文件、测试或可观察事实，不写 agent 自述。
- Description 不构成 auditor blocker；审核器只核冻结 criteria 与直接相关回归，未冻结人工体验只能成为 user review 建议。
- 任何关闭工具结果都返回 `details.completed=true` 与可读 display / `dgoal 完成信号`；不依赖额外 assistant 文本猜测完成。
- UI 更新失败只能降级提示，不能改变已持久化的状态事实。
