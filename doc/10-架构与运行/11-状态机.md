# 11 - 状态机

> 当前权威设计：Plan 与状态写入以 ADR 0038 为主，自动续跑语义选择与结构化活性熔断由 ADR 0045 补充；状态写入统一经 `plan_update`，check 只记录审核结果。

## Goal 状态

```text
Task Plan:          active ──last task done with evidence, declared-deliverable evidence, and completionReview──→ done
Phase/Goal Plan: pending ──proposal confirmed──→ active
                                      │
                                      ├── technical failure / user stop / agent blocker ──→ paused
                                      │                                                │
                                      └── all phases done + goal check approved        └──resume──→ active
                                          + update ──→ done
```

| 状态 | 含义 |
|---|---|
| `pending` | Phase/Goal Plan 正在语义预审或等待用户确认 |
| `active` | 当前 Plan 正在执行，或正在修复 rejected check |
| `paused` | 自动续跑停止，等待 `/dgoal resume` 或用户处理 |
| `done` | 完成守卫通过后收口：Task Plan 由最后一个 task 的 `plan_update` 原子收口；Phase/Goal Plan 由 `plan_update(target=goal,status=done)` 收口 |

完成后先持久化 done / 清空活动 Plan，再尝试更新 UI；TUI 异常不能阻断闭环。

## Phase 状态

```text
pending ──task 开始──→ in_progress ──完成守卫 + plan_update──→ done
   │                         │
   └────────阻塞─────────────┴──→ blocked ──解除──→ in_progress
```

中间状态可由 task 聚合，但 phase 不会因 task 状态聚合自动 done：

- Phase Plan：task 全部 `done` 后，`plan_update` 可写 phase done；blocked 表示尚未完成。
- Goal Plan：还必须有当前 phase revision 的 `phase_check=approved`。
- Task Plan：隐藏 phase 不作为工具状态目标；最后一个 task 带 evidence、声明交付物的逐项 evidence（如有）与同会话 `completionReview` 进入 done 时，运行时直接检查平铺 task 并自动关闭 goal。缺少任何一项时不写该 task 的 done。

## Task 状态

```text
pending ──→ in_progress ──→ done
   │               │
   └──────────────→ blocked ──→ in_progress
```

- 不能从 pending 跳过执行直接 done，也不能从 in_progress 回到 pending。
- done 必须带可独立复验的 `evidence`；声明 `deliverables` 时还必须有与每个 target 一一对应的 `deliverableEvidence`。Task Plan 的末任务另需 `completionReview`，确认已回读所有 task Description 与显式交付物；发现遗漏时新建 follow-up task。
- blocked 必须有 `blockedReason`；解除为 in_progress 时清除旧阻塞原因。
- 未完成依赖会阻止 task 进入 in_progress。

## Task DAG 读模型状态

Task DAG 的节点状态是从上述 phase/task 状态与 `blockedBy` 临时派生的只读投影，不是新的持久状态机：

- task 已 `done` → `done`；
- 当前 phase 已 `blocked` 时，所有未完成 task → `phase_blocked`，`ready` 与立即解锁边均为空，phase 的 `blockedReason` 成为共同根阻塞；
- 否则，task 自身已 `blocked` → `blocked`，且自身进入该节点的根阻塞集合；
- 否则，仍有未完成直接依赖 → `waiting`；
- 否则 → `ready`。

读模型只解释当前未完成 phase，不写状态、不增加 revision，也不改变 task/phase 的合法迁移。

## Check 状态

每次 check 写 `CheckRecord`：

```text
running → approved | rejected | audit_error
```

记录包含 scope、report、checkedAt 与 revision。phase check 使用所属 phase revision；goal check 使用全局 Plan revision。它与 phase/goal 状态正交：

- approved：允许后续 `plan_update` 通过对应完成守卫；不自动 done。
- rejected：Plan 保持 active，agent 修复；相关写操作增加对应 revision 后旧记录失效。
- audit_error：不是业务拒绝，goal 进入 `paused(audit_error)`。

## Revision

`task_plan` 替换、`plan_create`、会改变受审事实的 `plan_update` 都增加全局 Plan revision，并清理 goal check：

- task/phase 变化只增加所属 phase revision，使该 phase check 与 goal check 失效；
- phase done 等全局进度变化使 goal check 失效；
- 纯读不改变 revision；check 运行期间其对应 revision 若变化，本轮结果丢弃，不写回新 revision。

## Paused

Task Plan 的用户中断只停止当前响应：它保持 `active`，清理旧 continuation，下一条用户输入会重新注入当前 Plan；不要求 `/dgoal resume`。显式 Phase/Goal Plan 才把用户中断作为暂停，以保留用户对高保障执行链的明确停止权。

新运行时保留固定可靠性出口：

| `pauseReason` | 来源 | resume |
|---|---|---|
| `user_abort` | 用户中断显式 Phase/Goal Plan，或 `/dgoal pause` | 恢复原 Plan |
| `model_error` | 连续第 5 次主模型错误（成功工具推进会清零；第 1、2 次静默，第 3、4 次告警） | 恢复重试 |
| `audit_error` | 审核器候选耗尽/协议异常/timeout | 清理对应审核故障范围后重试 |
| `no_progress` | 连续 3 轮无工具，或连续 8 轮只有工具活动但没有观察到文件 / Plan 持久进展 | 清零两类空转计数后继续 |
| `agent_blocked` | `plan_update(target=goal,status=paused,reason=...)` | 保留原因，等待用户解除 |

Check 的业务拒绝不会切换 Goal 状态，也不会按固定拒绝次数自动暂停；Plan 持续保持 `active`，直到修复后重审或命中上述技术熔断。`/dgoal resume` 只有在恢复 prompt 成功入队后才保持 active；发送失败会恢复原 paused 原因，避免假恢复后永久停滞。

`no_progress` 是活性保护，不是语义审核（ADR 0045）。LLM 根据目标和上下文决定继续实际推进，或在真实用户决策死锁时结构化暂停；运行时不读取 assistant 文本，也不解析 `bash` 命令字符串，每轮只观察工具事件及结构化状态差。成功 `edit` / `write`、独立 check 终态，以及 task/phase/goal status、task evidence、blocked 结构或 Plan 任务集合变化视为持久进展；`read` / `plan_read` / `bash` / 未知工具、失败写入，以及仅修改 `objective` / `subject` / `description` 的文本更新只算活动。连续停滞时 continuation 会升级提示，要求 agent 直接执行或委派；真实用户决策死锁必须用 `plan_update(target=goal,status=paused,reason=...)` 结构化暂停，纯文字“被阻塞”不改变状态。LLM 若持续选择继续却没有持久进展，达到阈值后运行时强制暂停。
